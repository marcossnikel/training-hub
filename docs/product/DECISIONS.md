| D-012 | Accepted | Use Better Auth `1.4.18` with email/password and database-backed server sessions. Every product authorization check derives the local owner from that validated session; sign-up, sign-in, sign-out, expiry, and server-side session revocation are supported. No password-recovery email delivery is configured or promised. | The shared password gate could not establish tenant identity. Better Auth fits the local/libSQL boundary while keeping session authorization server-derived; recovery delivery needs a separate deliberate mail/configuration decision. | A reviewed recovery-delivery design, auth-provider migration, or session-security requirement changes the model. |
| D-013 | Accepted | Request exactly `read,activity:read_all,profile:read_all` and enforce the granted scope before a connection becomes usable. Strava makes the base public-profile `read` permission mandatory on its authorization screen; Training Hub additionally requires private-activity and full-profile read access and requests no write scope. While the owner has an active local connection, its encrypted connection material and imported/derived Strava data are retained. A user-initiated disconnect/delete request permanently removes that local material immediately. A provider revocation triggers the same removal only when Training Hub detects it, and a future account-deletion flow must invoke it; those implemented deletion paths complete promptly and no later than 30 days. The delivered product does not claim background provider-revocation detection or an account-deletion surface. A retained-history/pause-sync model is not accepted. | These are privacy and onboarding promises, not merely implementation details. | A written Strava policy clarification or reviewed account/provider lifecycle changes the contract. |
| D-014 | Accepted | Run the first beta as a manual, invitation-only cohort. Public landing copy explains the boundary but does not collect a waitlist, create an account, accept payment, or promise availability. New beta registration must be server-enforced by a valid private invitation before public promotion; current developer/test sign-up is not evidence of beta access. | A small invited cohort is safer while BYO setup and support are still being learned, but a copy-only gate would be unsafe. | A reviewed cohort/support result supports a broader entry model. |
| D-015 | Accepted | The first comparable-session insight is a deterministic **comparable prior activity**: one athlete's confirmed current activity matched to one of that same athlete's confirmed prior activities using only sport family, distance, and moving time. A reliable match requires distance difference less than or equal to 10% and moving-time difference less than or equal to 20%, each relative to the current activity. There is no limited-confidence tier. | Current summaries do not contain workout intent or a general training-block model. This gives an athlete a transparent, evidence-linked comparison without inventing a workout classification, equivalence, or coaching conclusion. | A separately accepted decision adds trustworthy workout classification, a general block model, or a new similarity input. |
| D-016 | Accepted | Each athlete registers the exact callback URL for the environment they are using with the Strava app they control. A deployed environment derives that URL only from its non-secret server-configured canonical HTTPS `TRAINING_HUB_PUBLIC_ORIGIN`; local development may derive only a direct loopback (`localhost`, `127.0.0.1`, or `[::1]`) request origin and ignores forwarded headers. It never accepts a browser-supplied callback or redirect URL. The current production canonical origin is `https://training-hub-psi-one.vercel.app`; it is not a substitute for the separate preview target required by #33. | The BYO beta path must not depend on a shared/founder app, a pre-provisioned public callback, or spoofable proxy headers. An athlete still configures their own app for every environment they use. | When a reviewed hosted Strava integration changes the connection model. |
| D-017 | Accepted | Disconnect attempts Strava deauthorization, then immediately and permanently deletes the current athlete’s local connection material and Strava-origin graph even when provider revocation cannot be confirmed. It preserves manually entered activities, goals, journals, athlete-entered profile values, manual gear, the account, and unrelated data. | Local privacy control must not be held hostage by an external provider response. | A reviewed provider lifecycle or data-origin model changes the deletion inventory. |
| D-018 | Accepted | The beta has one monthly plan targeted around US$5, with no trial, coupon, annual plan, tier, tax automation, or live billing. A verified Stripe webhook and reconciled subscription record—not a Checkout return—are authoritative for entitlement. A current verified active subscription, and a previously verified cancellation-scheduled subscription before its paid-through boundary, have full access. An auto-renewing active record that is stale or unavailable at or after its prior paid-through time is `unknown` and restricted until renewal is verified; only a cancellation-scheduled record becomes canceled/expired at that boundary. Incomplete, past-due, unpaid, canceled/expired, delayed, unrecognized, or provider-unavailable states fail closed for paid capabilities while preserving sign-in, private data controls, disconnect, deletion, and read-only access to the athlete’s own existing training records. Stripe work begins in isolated test mode only; live activation needs a separate explicit founder approval. | The first paid beta needs one understandable offering and a failure boundary that cannot make payment redirects authoritative, leak data, or trap an athlete’s own data. | A separately reviewed payment-readiness decision changes price, plan shape, access policy, Stripe operating mode, or the data-control boundary. |
| D-019 | Accepted | First-login onboarding and post-Strava-connection activation are separate one-time, skippable experiences. Welcome completion/skip is persisted independently of connection state. Closing post-connect activation dismisses only its interface; import continues or resumes. | The platform can be introduced before a connection, while the data-specific explanation belongs to the moment real history arrives. | Beta observation shows a different activation sequence is clearer. |
| D-020 | Accepted | Initial Strava history imports as confirmed using one persisted server cutoff; only activities starting after that cutoff enter Review. Import retry is idempotent and cannot move the cutoff or skip older pages. | Historical Inbox flooding prevents first value and leaves log/performance empty. | Provider semantics or the accepted meaning of Review changes. |
| D-021 | Accepted | Post-connect Activation Summary uses actual import stages/counters and summary-derived facts: sport counts, imported date range, explicitly bounded totals, consistency, gear state, calculated estimates, and confirmable hypotheses. Year-to-date wording is allowed only when an effective validated athlete timezone exists; otherwise the UI names the exact date range. Motion may communicate real work but cannot invent progress or certainty. | The athlete should see immediate, trustworthy value instead of a blank dashboard or decorative loader. | Product measurement shows a different first-value surface performs better. |
| D-022 | Accepted | Athlete performance parameters are nullable, unit-aware, editable, and provenance-bearing (`athlete_entered`, `provider`, `calculated`, or `analyst_hypothesis`). Derived values retain formula/version and source evidence; no founder-specific value is a product default. | Performance calculations must distinguish facts, estimates, and unknowns. | A new calculation requires a revised typed field/provenance contract. |
| D-023 | Accepted | Application roles are `creator` and `member`. Creator receives only named operational capabilities such as environment visibility and invite management; it never broadens owner scope or grants access to another athlete's data. | Founder operations need authorization without introducing a tenant superuser. | A deliberately designed support, organization, or team model is accepted. |
| D-024 | Accepted | Activity periods use the persisted Strava `started_at_local` day when available and UTC start only as fallback. Relative calendar labels such as `this year` use an effective validated IANA timezone with provenance: athlete-entered override, then a canonical IANA identifier safely parsed from connected-provider data; a numeric UTC offset alone is never sufficient. Without a valid timezone, summaries show exact date bounds instead of guessing. | Period boundaries and first-value claims must not shift with the server/browser timezone or silently describe a different athlete day. | A broader locale/calendar model is accepted. |
| D-025 | Accepted | Gear has explicit `manual` or `strava` origin. For Strava-origin gear, the current odometer is the latest non-negative provider-reported lifetime distance with observation time; confirmed local activity assignments are evidence/breakdown and are not added again. Manual gear keeps `initial_km + confirmed local mileage`, with any linked provider odometer shown only as a separate reference. Unknown or stale provider distance stays unknown/stale, never zero. Disconnect deletes Strava-origin gear and clears provider-derived fields/mappings from manual gear. | Combining a provider lifetime odometer with local splits would double-count history and delayed activities. Separate source-labelled measures keep mileage truthful and preserve manual gear. | A reviewed multi-provider or gear-reconciliation model changes the source of truth. |

## Decision protocol

Marcos owns accepted product changes. A planning session makes the decision and
task packet explicit; a builder executes it and resolves recoverable local
failures without silently overturning an Accepted decision. Record a changed
trade-off here before implementation. Separate review is optional and happens
only when Marcos requests it.
